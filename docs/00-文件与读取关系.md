# 00 文件与读取关系

谁读哪个文件、读哪些字段、读不到怎么办。**改字段名必须三端同改**——清单、启动器、下载器是一套契约，单边改名会让对面静默不动。

## 一张表

| 读取方 | 读哪里 | 只取哪些字段 | 拿不到时怎么办 |
|---|---|---|---|
| 更新器（启动器） | `res/latest.json` | `schema` / `channel` / `client_version` / `min_version` / `install_order` / `assets[]` 里 **`kind` 为 `patch` 或 `shell` 的那几条** | 三条源都失败 → 保留本地版本，界面提示"检查更新失败"，**不推进、不删除任何文件** |
| 启动器（自更新） | `app/launcher/latest.json` | `version` / `size` / `sha256` / `url` | 同上下载失败则跳过自更新，不影响主流程 |
| 下载器 | `res/latest.json` | **全部 kind**（`baseline` / `shell` / `patch`）+ `install_order` | 清单 404 或 `schema != 1` → 直接报错退出，**不进入下载** |
| 下载器（anondrop 源） | `res/anondrop-map.json` | `{文件名: 直链}`，按 `parts[].name` 查表 | 查不到就跳过该源，其余源照跑 |
| 下载器（逐卷） | `parts[]` | `index` / `name` / `size` / `sha256` | 缺 `sha256` → 该卷判为不可信，**拒收** |
| 安卓壳 | `app/latest.json` | `version_code` / `version_name` / `apk` / `size` / `sha256` | 与本清单无关，独立链路 |

## 为什么现在没有补丁

`res/latest.json` 里现在一个 `kind == "patch"` 的资产都没有，这是刻意的，不是漏配。

三条边界先划清：

- **内容版本**（`client_version`）只反映**内容**。分卷里的资源变没变，看它。
- **壳版本**（启动器 `1.0.35`、下载器各自的 `1.0.X`）与内容版本完全独立，**只走 `kind == "shell"` 的自更新通道**，不再通过补丁分发壳。
- **补丁**（`kind == "patch"`）只用于**真实的内容增量**——资源文件变了、且增量远小于整包时才发。

### 反面教材（2026-11-04 实案）

`1.0.20261102.1 → 1.0.20261102.2` 这个补丁，`version.json` 原话是"客户端内容未变，本次只更壳"，也就是说两端**内容完全相同，没有需要补的东西**。而补丁包里装的却是 `ONETAP启动器.exe`（8,443,032 / `7a974d25…`），现役启动器是 8,498,546 / `9b5873a2…` —— 比补丁里那个**更新**。

按设计意图，装这个补丁的后果是：补丁把启动器降到 `7a974d25` → 启动器自更新发现版本旧 → 从 `app/launcher/` 再拉一次 → 升回 `9b5873a2`。**来回抖一次，白耗 8MB，净变化为零**，中间任一步校验失败就停在被降级的那一版。

实现上还有兜底，**三个分支的出口都是"壳保持原样"**，区别只是玩家有没有感知：

| 分支 | 条件 | 结果 |
|---|---|---|
| 1 | 目标路径 == 正在运行的 exe | 跳过覆盖，只写临时 `<exe>.new`；换壳只认 `appdata/update/<exe>.new`，那份永远换不上 → **壳不变，无感** |
| 2 | 路径判据未命中（装在非默认目录、路径写法不同等） | `shutil.copy2` 写一个**正在运行的映像**，Windows 直接拒绝（`copy2` → `[WinError 32]`；`open('wb')`/`open('ab')` → `PermissionError` Errno 13，同一个 cause 两种表层错误码，取决于调用方式）→ 异常 → `_rollback()` **撤销本次写入**（不是重写整份内容，见下）→ **壳不变，玩家看到一次"更新失败"** |
| 3 | 该文件落在 `postcheck.must_sha256` 抽查名单 | 写入后校验必挂 → `_rollback()` 撤销本次写入 → **壳不变** |

`_rollback()` 的范围要看清：它只撤销**本次已写过的文件 + 本次新建的文件**（备份清单 + created 列表），**不是恢复整份客户端**。所以"回滚"的代价是几 MB，不是 15GB。

也就是说，"不降级"由两层保证：**代码层判据**（分支 1，延后写 `.new`）+ **OS 层执行中映像不可写**（分支 2，写打开必然 sharing violation）。代码层判据确实是实现细节、不应作为设计依据；但即使它失效，OS 层兜住的是"更新失败并回滚"，而不是"降级"。

真正的残余风险不是降级，而是 `deleted[]` / `renamed[]` 里误列了内容文件——那是会真的删错的。所以"补丁 `files[]` 里不许出现任何壳程序"这条硬规则照旧，见 `02-发版流程.md` §3.3。

所以现在的处置是：补丁文件**保留在 release 里备查**（`v1.0.20261102.1`，第 39、40 个资产），但**不放进 `assets[]`**，线上清单里 `patch` 计数为 0。壳要更新就发 `shell`，内容要更新就发 `patch`，两者不混。

## 更新器只取 patch 和 shell，不碰 baseline

启动器体积只有 8MB 量级，它**不**下载 `baseline`（15GB 级，只有下载器能下）。同一份 `res/latest.json` 由启动器**两个入口**分别消费，走两条完全不同的执行路径：

| 类别 | 启动器入口 | resmanifest 函数 | 走向 | 落地方式 |
|---|---|---|---|---|
| `patch` | `updater.plan_updates()` | `patch_chain()`：只筛 `kind=patch` | 进更新计划，按 `install_order` 串 `from→to`，链断了提示用下载器重装 | 校验后解压覆盖内容文件 |
| `shell` | `launcher.fetch_launcher_sec()` | `shell_asset()`：筛 `kind=shell` 且 id 前缀 `shell-launcher-` | 不进计划，整壳对齐（`shell_update_loop()` 开机查一次、之后每小时一次） | sha256 相等 → `current` 只记账；不等 → 下载校验后写 `<exe>.new`，重启生效 |

`shell` 不出现在 `plan_updates()` 返回的步骤列表里，**是设计如此，不是没实现**。壳没法"被应用"——它要替换正在运行的那个进程，只能走 `.new` → 改名 → 重启这一套。混进补丁链就会拿壳去覆盖内容目录，那是事故。

```
res/latest.json
  ├─ plan_updates()       筛 kind=patch → 内容补丁链（按 from 匹配，sha256 通过才解压覆盖）
  └─ fetch_launcher_sec() 筛 kind=shell → shell_self_update() → <exe>.new → 重启替换自身
```

两者都不消费 `kind=baseline`。`install_order` 里的 `baseline` 对更新器是"看得见但不处理"的条目，保留它是为了让下载器和更新器**共用同一份清单**，不必维护两个文件。

### 实现去哪看（`resmanifest.py` 公开函数）

| 函数 | 作用 |
|---|---|
| `fetch_res_manifest()` | 拉取 `res/latest.json`（三路竞速，`ghapi` 权威，见 `03-资源通道与测速基线.md`） |
| `patch_chain()` | 筛 `kind=patch`，拼出内容补丁链 |
| `shell_asset()` | 筛 `kind=shell`，默认认 `shell-launcher-` 前缀 |
| `source_urls()` | 按 `type` 白名单展开某资产的下载地址（含镜像派生） |
| `kind_counts()` | 按 `kind` 统计资产数量，用于自检与日志 |

## 下载器读全部，顺序即覆盖顺序

```
for id in install_order:          # 数组顺序 = 安装顺序
    下载该 asset 所有 parts
    逐卷校验 parts[].sha256        # 任一卷不符 -> 该卷重下，重下仍不符 -> 整体失败
    拼接/解压
    覆盖到目标目录                 # 后项覆盖前项
```

顺序约定固定为：

1. `baseline-*` —— 打底，整包铺开
2. `shell-*` —— 覆盖旧的壳程序
3. `patch-*` —— 最后叠补丁，补丁内容优先级最高

所以补丁里带同名文件时**一定是补丁赢**。反过来说，补丁里不要放"整包才该有的目录结构"，只放差异文件；**壳程序永远不许进补丁**（见 `02-发版流程.md` §3.3）。

## 为什么清单是唯一入口

- 启动器、下载器读同一个 `res/latest.json`，发版只改一个文件；
- 渠道地址不写在程序里，全在清单的 `sources[]`，换线路不用重新发包；
- 校验值也不写在程序里，`parts[].sha256` 是唯一依据。

## 目录里各文件的作用

| 路径 | 作用 | 谁写 |
|---|---|---|
| `res/latest.json` | 统一资源清单，程序读取入口 | `make_res_manifest.py` 生成，不手改 |
| `res/anondrop-map.json` | 单文件直链平表，仅 `type=anondrop` 使用 | 同上，自动生成 |
| `app/latest.json` | 安卓壳自身版本 | 壳的发布流程 |
| `app/launcher/latest.json` | 启动器自身版本（含 `url`） | 启动器发布流程 |
| `app/launcher/ONETAPLauncher.bin` | 启动器二进制 | 启动器发布流程 |
| `app/downloader/latest.json` | 下载器自身版本（目录按需建立） | 下载器发布流程 |
| `docs/` | 人看，程序不读 | 手写 |
