# 01 版本号规则

仓库里同时存在三套版本号，命名空间互相独立。

## 三套规则

| 对象 | 形如 | 规则 | 例子 |
|---|---|---|---|
| 主程序（整包） | `1.0.YYYYMMDD.N` | 日期 + 当日序号，`N` 从 1 起 | `1.0.20261102.1`、`1.0.20261102.2` |
| 壳（启动器 / 下载器） | `1.0.X` | 纯递增整数，与日期无关、与主程序解耦 | `1.0.35`、`1.0.36` |
| 补丁 | `from → to` | **没有独立版本号**，用两端版本描述 | `1.0.20261102.1 → 1.0.20261102.2` |

补充约定：

- 主程序版本号只在**整包内容变化**时递增。只换壳、不发补丁的发布，`client_version` 也会动，但 `baseline` 的 `version` 不动（见下条）。
- `baseline` 资产的 `version` 是**整包自己的版本**，可能小于清单顶层的 `client_version`。例如清单 `client_version = 1.0.20261102.2`，而 `baseline.version = 1.0.20261102.1` —— 意思是"用 11-02 的整包打底，再叠补丁到 .2"。这是正常状态，不是写错了。
- 壳的版本号每个壳各自独立递增。启动器到 `1.0.35` 不代表下载器也是 `1.0.35`。

## 核心规则：版本号互不比较大小，只比 sha256

判断"要不要装"只有一条依据：

```
要装  <=>  目标文件的 sha256 != 本地同路径文件的 sha256
```

`version` 字段**只用于显示和日志**，任何分支逻辑都不许拿它做大小比较。

### 为什么禁止比较大小

三套命名空间混在一起比，必然出错：

| 比较 | 朴素做法 | 结果 | 后果 |
|---|---|---|---|
| `1.0.36` vs `1.0.20261102.2` | 按 `.` 分段比第二段：`0` vs `20261102` | `1.0.36` 被判为**更旧** | 壳实际是新的，却被判旧 → 永远不更新 |
| 同上 | 转 float：`1.0.36 < 1.0.20261102.2` | 同上判旧 | 同上 |
| `1.0.9` vs `1.0.10` | 字符串比较：`"1.0.9" > "1.0.10"` | `1.0.9` 被判为**更新** | 旧壳覆盖新壳，直接回退 |
| 补丁 `from→to` | 没有可比的单一数值 | 无法比较 | — |

同一个错误在不同版本对上表现相反（一次"该升不升"，一次"不该升却升"），排查时很难联想到是版本比较的锅。sha256 没有这个问题：**内容变了哈希必然变，内容没变哈希必然相同**，跨命名空间、跨日期、跨壳都成立。

### 唯一允许比较版本的地方

`min_version`：

```
if local_client_version < min_version:
    必须整包重装，不接受补丁
```

这是刻意保留的硬闸——某些结构变更无法用补丁跨过，只能用一整包兜底。它只比**主程序版本**，且只做"低于就强制整包"这一件事，不参与日常更新判定。

## 落地检查表

发版前逐条过：

- [ ] 改了内容 → 换了版本号；没改内容 → 版本号不动（`released` 可以动）
- [ ] 更新了 `parts[].sha256`（内容一变，逐卷哈希必须重算）
- [ ] 更新了 `total_sha256`
- [ ] 补丁的 `from` 是**当前线上版本**，不是上一个补丁的 `to`
- [ ] 没有在任何地方写"如果版本号大就覆盖"这类逻辑
