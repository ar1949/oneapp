# 02 发版流程

三种发布各走一条路。**顺序固定：先传文件，再改清单**。反序的结果是清单指向一个还不存在的文件，所有读清单的程序当场失败。

## 0. 通用前置

```bash
cd D:/work_zh
python -c "import gh_token_helper as t; print(bool(t.get_token()))"   # 必须 True，token 不落盘
curl -sS --noproxy '*' -o /dev/null -w "%{http_code}\n" https://api.github.com/repos/ar1949/oneapp
```

`api.github.com` 通、`github.com:443` 不通是常态，所以**所有写操作走 Contents API**（`gh_api.put_file`），不要试 `git push`。

## 1. 发新版壳（启动器 / 下载器）

壳是单文件 + 一个 `latest.json`，最轻。用现成脚本，不要手工拼：

```bash
# 启动器：打包 -> 传 app/launcher/ONETAPLauncher.bin + latest.json -> 打 tag launcher-v<ver>
python release_launcher.py --dry-run 1.0.36 "改了什么"
python release_launcher.py 1.0.36 "改了什么"

# 下载器：同上，目录换成 app/downloader/
python release_downloader.py --dry-run 1.0.0 "改了什么"
python release_downloader.py 1.0.0 "改了什么"
```

壳发完**必须**重跑清单，否则 `res/latest.json` 里的 `shell-*` 还是旧版本、旧 sha：

```bash
python make_res_manifest.py --dry-run --version 1.0.20261102.2      # 先看
python make_res_manifest.py --version 1.0.20261102.2 --publish      # 再发
```

检查点：清单里 `shell-launcher-*` 的 `total_sha256` 必须等于 `app/launcher/latest.json` 里的 `sha256`，不等就是打包和清单对不上，**停下别发**。

## 2. 发新版整包（主程序）

```bash
# 2.1 切卷（419430400 字节/卷），生成 parts.json + 每卷 sha256
# 2.2 37 卷 + parts.json 上传为 release 资产（tag: v<版本>），逐个确认 uploaded
# 2.3 服务器侧落盘：逐卷实算 sha256 与 parts.json 对账，只替换 version.json 的 parts 段
python - < publish_parts.py
# 2.4 只有上一步全过，才生成并发布清单
python make_res_manifest.py --dry-run --version 1.0.20261103.1
python make_res_manifest.py --version 1.0.20261103.1 --notes "本次改了什么" --publish
```

清单自检会挡住这些错：`sum(parts.size) != total_bytes`、`index` 不连续、`sha256` 不是 64 位小写 hex、`install_order` 里的 id 不存在、**`baseline` 分卷名不符合 `<前缀>.partNN` 或前缀不唯一**（shell / patch 是裸名单文件，不受此约束）。任何一条不过都不发布。

最后那条校验是给一个**隐式约定**上的保险：清单的 `assets[]` 里刻意没有 `name` 字段，下游靠 `parts[0].name` 去掉 `.partNN` 反推整包名。这个推法唯一且稳定，但前提是分卷命名不能被人改——所以让它在发布时就炸，而不是等下载器算出一个不存在的包名。

## 3. 发新补丁（以及什么时候根本不该发）

补丁是 `from → to` 的差异包，只在**两端版本都在线上**、且**内容真的变了**时有意义。

### 3.1 什么时候该发补丁

- `baseline` 的内容变了：换模型、换贴图、改配置、加资源；
- 增量**远小于**整包（几百 MB vs 15GB 级），否则不如直接发新整包；
- 两端 `client_version` 之间的**内容**确有差异，且能写清差异清单。

### 3.2 什么时候**不该**发补丁

- **只改了壳**（启动器 / 下载器 exe）→ 发 `shell` 资产，让壳走自更新。壳和内容是两个版本序列，混在一起就会互相打架。
- 两端内容完全相同（比如 `version.json` 写着"内容未变，本次只更壳"）→ 没有可补的东西，发了就是空转。
- 补丁里会带上比现役更旧的壳 → **等于降级**，装完再由自更新升回来，来回抖一次，净变化为零；中间任一步失败就卡在降级版。

### 3.3 生成补丁的硬检查

打包脚本里必须显式排除壳程序。补丁的 `files[]` 里**不许出现**：

- `ONETAP启动器.exe` / `ONETAPLauncher.exe` / `ONETAPLauncher.bin`
- `ONETAPDownloader.exe` / `ONETAPDownloader.bin`

出现任意一个就判为打包错误，直接中止。补丁只装**内容文件**。

顺带对账：补丁的 `files[]` 里每个文件的 `sha256`，必须和 `baseline` 对应路径的 `sha256` 不同——全部相同说明"没有差异"，这个补丁应当作废。

### 3.4 发布命令

```bash
# 3.4.1 生成 diff 包（已排除壳），记下 size / sha256
# 3.4.2 上传到 release，文件名 ONETAP_patch_<from>_to_<to>.zip，同名 .json 平级同目录
# 3.4.3 写进 version.json 的 patches 段（from / to / url / size / sha256）
# 3.4.4 发布清单
python make_res_manifest.py --dry-run --version 1.0.20261103.1 --patch-tag v1.0.20261103.1
python make_res_manifest.py --version 1.0.20261103.1 --patch-tag v1.0.20261103.1 --publish
```

`--patch-tag` 必须指向**真的已上传该资产**的 release，否则 `github` / `ghproxy` 两条源全 404，只剩网盘源能救。

**zip 和同名 `.json` 必须一起传。** 客户端按 `url 同目录 + 同名 + .zip→.json` 推元数据地址，只传 zip 不传 json，客户端会报"补丁元数据取不到，请运行下载器重新安装"，让玩家白跑一趟 15GB。两个文件、同一个 release、同一次操作。

生成器在发补丁前会**实算本地 zip 的 size / sha256**，与 `version.json` 的 `patches[]` 逐项比对，不一致直接拒绝发布：

```
补丁文件与 version.json 记录不一致：本地 8266723 / 91412213ee22…，记录 8265367 / 365332f611b6… —— 先确认哪个是正本，别发
```

这条闸不是形式主义。2026-11-04 真的出现过同名同路径但不同字节的两版补丁（`version.json` 记的哈希对应服务器上玩家实际在用的那一版，盘上那个是当晚重生成的、从没部署过），如果照 `version.json` 发出去，清单里的哈希和真文件对不上，客户端逐卷校验必然失败，且 fail-closed 不报错，玩家只会看到"更新没反应"。**先确认正本，再发。**

## 4. 回滚

清单是唯一入口，回滚就是"把清单指回上一个已知良好状态"：

```bash
# 4.1 用旧参数重新生成（版本号、notes 都填回旧的）
python make_res_manifest.py --dry-run --version 1.0.20261102.1 --released "2026-11-02 10:17:00"
# 4.2 确认 baseline / shell / patch 的 sha256 都是旧值
python make_res_manifest.py --version 1.0.20261102.1 --released "2026-11-02 10:17:00" --publish
```

**不要删 release 资产、不要删 tag、不要改历史文件**。旧清单指向的资产只要还在，回滚就是一次 `PUT`。

## 5. 发坏了怎么办：禁止 force-move tag

这是本仓库最贵的一课，写在最显眼的位置。

**现象**：发版后一部分人更新完了、另一部分人永远停在旧版，界面不报任何错，"检查更新"显示已是最新。

**成因链**：

1. 有人把 `launcher-v1.0.35` 这个 tag 移到新 commit（`PATCH /git/refs/tags/... force=true`，或本地 `git push -f --tags`）。
2. 壳的自更新地址是 `jsdelivr.net/gh/ar1949/oneapp@launcher-v1.0.35/...` —— **CDN 按 `tag@commit` 缓存**。tag 换了指向，CDN 上的旧对象不会立刻失效，仍返回**旧字节**。
3. 程序拿到旧字节，算 sha256，和 `latest.json` 里的新 sha256 不等。
4. 校验是 **fail-closed**：不匹配就不安装、删临时文件、**静默跳过**（不弹错误——避免玩家看到一堆哈希）。
5. 结果：`latest.json` 说"有新版本"，下载链路每次都给旧文件，永远校验不过。玩家侧表现为"点了没反应"，日志里只有一行 sha 不等。

**正确做法**：

| 场景 | 做法 |
|---|---|
| 想改已发布的壳 | **发新版本号**（1.0.36），打**新 tag**，旧 tag 原地不动 |
| 包传错了 | 用**新版本号**重发；确需覆盖同名资产时只替换 release 资产，**tag 不动** |
| 非要让旧 tag 指新 commit | 不允许。这不是"高级操作"，是把所有已发出去的客户端锁死 |
| 已经误移了 tag | 把 tag 移回原 commit，然后**立刻发一个新版本号**；只回移 tag 不够，CDN 缓存已经脏了，恢复时间不可控 |

判断依据一句话：**tag 是不可变引用，版本号只能前进。** 想让内容变，就换版本号。

## 6. 发版前检查清单

- [ ] `--dry-run` 的输出逐字看过，`parts` 数量、`total_bytes`、`total_sha256` 都对
- [ ] 走 `--publish` 前确认 `install_order` 顺序是 `baseline → shell → patch`
- [ ] 没有 force-move 任何 tag
- [ ] 没有改动 `app/` 下已发布的二进制（要改就发新版本）
- [ ] 清单发完，用 `res/latest.json` 的第一条 source 手工拉一卷，sha256 对得上
- [ ] 验收**只看 `api.github.com`**（contents 解码），不要用 jsDelivr —— 镜像缓存会滞后十几分钟，拿它验收会误判"没发成功"然后重复发
- [ ] **PUT 返回 200 不等于写对了**：必须回读同一路径，`sha256(回读内容) == sha256(本地生成文件)` 才算成功。只比字节数不够——出现过内容变了但长度一模一样（10593 → 10593）的情况，长度对得上照样是旧的

那条回读校验最短的写法：

```python
import base64, hashlib, sys
sys.path.insert(0, "D:/work_zh")
import gh_api, gh_token_helper

tok = gh_token_helper.get_token()
path = "res/latest.json"
local = open("D:/work_zh/.resout/latest.json", "rb").read()
code, body = gh_api.curl("GET", "%s/repos/%s/contents/%s?ref=main" % (gh_api.API, gh_api.REPO, path), tok, timeout=60)
remote = base64.b64decode(body["content"])
print(code, len(remote), hashlib.sha256(remote).hexdigest() == hashlib.sha256(local).hexdigest())
```

## 7. 发内容补丁前，先在客户端预演一遍

补丁最贵的失败不是"传错文件"，是**传对了但客户端判成整包**：`assets[]` 里那条 patch 少了 `from` / `to`、或 `parts[0].sha256` 为空，`patch_chain()` 建不出索引，会**静默降级成整包**，不报错、不提示，玩家白下 15GB。

所以真发之前，先在客户端侧用**合成清单**跑一次（copy 线上清单、只往内存里塞 patch 资产，不发布、不落盘）：

```bash
cd /d/clients/PC/launcher && python - <<'PY'
import sys, os, copy
sys.path.insert(0, os.getcwd()); sys.path.insert(0, r"D:\work_zh")
import resmanifest as R, updater as UP
import make_res_manifest as M

man = R.fetch_res_manifest(force=True)
vj = M.load_json(r"D:\clients\publish\version.json")
patch = M.build_patch(vj, "<目标版本>", "v<目标版本>", [])   # 生成器真产出的资产

man2 = copy.deepcopy(man)
man2["client_version"] = "<目标版本>"
man2["assets"].append(patch)
man2["install_order"] = [a["id"] for a in man2["assets"]]   # id 必须进 order

print("kinds =", R.kind_counts(man2))
mode, chain = UP.plan_updates(man2, "<当前线上版本>")
print("plan =", mode, [(s["from"], s["to"], s["size"], s["sha256"][:12]) for s in chain])
for s in chain:
    print("  zip :", s["urls"])
    print("  meta:", s["meta_urls"])
PY
```

三条判读标准，**全过才能真发**：

1. `plan` 必须是 `patch` 且步数为预期值 —— 返回 `full` 就说明 patch 资产没被 `patch_chain()` 认出来（缺 `from` / `to`，或 `sha256` 为空）；
2. `install_order` 里必须含该 patch 的 `id`（不在 order 里的 patch 排序不可控，一条以上就会乱）；
3. 打印出的 `zip` / `meta` 两条 URL，去掉 `https://gh-proxy.com/` 前缀后能在浏览器直接下 —— 也就是 **zip 和同名 `.json` 都真实存在**，缺一个客户端就只能报"补丁元数据取不到"。

这套预演 2026-11-04 实际跑过：合成清单下 `plan_updates` 正确返回 1 步 patch，`zip` / `meta` 两条镜像 URL 都能从 `url 目录 + 同名 + .zip→.json` 自动推出来。**先预演，再发布**，比"发完看玩家反应"便宜太多。
