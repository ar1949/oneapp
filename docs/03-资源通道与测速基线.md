# 03 资源通道与测速基线

四条通道同时可用，程序按 `sources[].weight` 分配线程。下面的数字是 **2026-11-04 本机家宽实测**，不是标称值；换网络环境要重测，重测后同步改这份文档和清单里的 `weight`。

## 实测速度

| 通道 | 单连接 | 4 并发合计 | Range 支持 | `weight` | 定位 |
|---|---|---|---|---|---|
| 网盘 CDN（`type=fj`） | 1.5 MB/s | **6.2 MB/s** | 支持 | 100 | 主力 |
| `gh-proxy`（`type=ghproxy`） | 0.4 ~ 2 MB/s 波动 | ~3.9 MB/s | 支持 | 60 | 主力备份 |
| 直连 GitHub（`type=github`） | 39 KB/s | — | 支持 | 40 | 兜底（海外/代理环境才快） |
| AnonDrop（`type=anondrop`） | 19 KB/s | — | **不支持** | 5 | 最后兜底，接近不可用 |

`weight` 是**相对权重**，下载器拿它乘该通道的实测速度来算分段配额。100 : 60 : 40 : 5 的含义是：正常网络下网盘吃掉绝大部分分片，`gh-proxy` 分担一部分，直连只在前面都失败时才起量，AnonDrop 基本不参与并发、只在全部失败后单线程顶一下。

## 清单本身的可达性（`res/latest.json`，11KB 量级）

清单是所有程序的第一步，它挂了后面全白搭，所以单独测。用线上真实清单、三路并行竞速：

| 路由 | 实测耗时 | 说明 |
|---|---|---|
| `ghapi`（`api.github.com` contents） | 1828 ms | 首字节慢，但最稳 |
| `gcore`（`gcore.jsdelivr.net`） | 3216 ms | 最慢，别放第一位 |
| `cdn`（`cdn.jsdelivr.net`） | 1385 ms | 单路最快 |
| **三路并行竞速** | **602 ms，命中 `ghapi`** | 并发取先到的，比任何单路都快 |
| 缓存命中 | 0.0 ms | 内存里已有就不再发请求 |

结论：清单走**三路并行竞速**，不要串行回退——串行最差情况是 1828+3216+1385 ≈ 6.4s，并行只要 0.6s。

**`raw.githubusercontent.com` 在本机 DNS 直接失败（秒断），必须从清单路由里排除。** 它只能用来取壳和补丁这类**文件**，且在所有路由里**排最后**；取清单本身绝不能用它。

## 逐条的坑

### 网盘 CDN（fj）

- 入口是 `share`（分享 id）+ `folder`（目录 id），不是直链；下载器要先列目录再按 `parts[].name` 匹配文件名。名字对不上就是取不到，**不要靠顺序猜**。
- 目录里除 37 卷之外还有 `parts.json`，它一样要取——那是卷数/总字节的第二份佐证。
- 好处：支持 Range 且单连接就不慢，是最适合做并发分段的通道。
- 坑：分享失效时整条通道静默变 0，不会报"链接过期"，表现为逐个文件超时。所以要**先探一个 HEAD/首字节**再决定是否给它 100 的配额。

### gh-proxy

- 形如 `https://gh-proxy.com/https://github.com/<owner>/<repo>/releases/download/<tag>/<file>`，前缀整段拼在原始 URL 前面。
- 速度波动最大：同一卷可能 0.4 MB/s，也可能 2 MB/s。分配线程时**不要**按峰值给满，否则尾部会被最慢的那个分片拖住。
- 支持 Range，可以重试单个分片。
- 坑：它会跟随 GitHub 的 302；如果目标 tag 被移走，转发层缓存可能仍返回旧字节 —— 与 §02 的 tag 不变原则是同一件事的两面。

### 直连 GitHub

- 国内实测 39 KB/s，15GB 整包按这个速度要 4 天多，只能在别的通道全挂时用于**小文件**（`latest.json`、补丁、壳）。
- 支持 Range。
- 坑一：`api.github.com` 稳定（清单竞速里 1828ms 命中），但 `raw.githubusercontent.com` 在本机 **DNS 直接失败、秒断**。所以清单路由必须排除 raw；壳/补丁的 `base` 虽然写 raw + 定死 commit，但前面必须压一条 `gh-proxy` 转发，raw 只做兜底且排最后。
- 坑二：壳文件的 `base` 用 **commit 定死**而不是分支。分支会随提交漂移，内容和 `sha256` 立刻脱钩，CDN 缓存也对不上。

### AnonDrop

- **不支持 Range**：只能从头拉整文件。37 卷、每卷 400MB，一卷失败就是整卷重来，没有断点续传。
- 会返回 520（Cloudflare 侧错误），重试也未必好，属于"过一会儿可能自己好"的类型。
- 单连接 19 KB/s，属于象征性可用。
- 因为它不支持 Range，下载器**不能**把它算进并发的分片配额；`weight=5` 的作用是"排在最后、且只按单线程整取"。
- 链接是逐文件的，所以单独放 `res/anondrop-map.json`（`{文件名: 直链}` 平表），而不是塞进 `sources` 数组。

## 优先级排序依据

1. **支持 Range 且单连接快的排前面**（fj）：能并发、能重试单片、失败代价小。
2. **支持 Range 但速度波动的排中间**（ghproxy）：可以并发，但配额要保守。
3. **支持 Range 但极慢的排后面**（github）：留着救急，别让它抢配额。
4. **不支持 Range 的排最后**（anondrop）：不给并发配额，只在全挂时整取。

程序侧的取舍原则：**任一通道连续失败 3 次就把它在本次会话里的权重降到 0**，不要每卷都重试一遍死掉的通道 —— 37 卷 × 3 次超时足够让整个安装看起来像卡死。

## 重测方法

```bash
# 单连接
curl --noproxy '*' -o /dev/null -w "%{speed_download}\n" -r 0-104857599 <url>
# Range 支持：返回 206 才支持，200 说明被忽略
curl --noproxy '*' -sS -o /dev/null -w "%{http_code}\n" -r 0-1023 <url>
```

`-r` 请求返回 `206` = 支持 Range；返回 `200` = 忽略 Range、整文件给你（AnonDrop 就是这样）。测速一律取 100MB 区间，不要用整个文件。
